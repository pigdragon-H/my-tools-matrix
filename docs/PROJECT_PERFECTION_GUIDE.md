## 🎯 項目理解

### 項目本質

工具矩陣不是「計算機集合」，而是「決策助手系統」。

每個工具都在「決策路徑」中扮演特定角色：

```
用戶問題 → 工具計算 → 結果解釋 → 下一步指引 → 決策完成
```

### 用戶心智模型

用戶進入工具頁面時的三個問題：

1. **「我應該輸入什麼？」** → 清晰的表單標籤和幫助文本
2. **「結果是什麼意思？」** → 結果解釋和上下文
3. **「接下來怎麼做？」** → 明確的下一步指引

### 設計目標

- ✅ **有用性優先** > 美觀性
- ✅ **用戶成功** > 功能完整
- ✅ **決策支持** > 單純計算

## 🔴🟡🟢🔵🟣 5 層規則系統

### 🔴 第 1 層：項目理解

**目的**：確保 AI 理解項目的本質和目標

**必須理解的內容**：

1. **項目在決策路徑中的位置**
   - 例如：BMR 是「身體指標 → 熱量規劃」的樞紐
   - 例如：BMI 是「快速評估」的獨立工具

2. **用戶的核心需求**
   - 用戶為什麼來這個工具？
   - 用戶期望得到什麼結果？
   - 用戶接下來會做什麼？

3. **項目的特殊複雜性**
   - 是否有多個計算公式？
   - 是否需要多步驟流程？
   - 是否需要跨工具數據同步？

**BMR 特例**：
- BMR 是決策路徑的樞紐（連接身體指標和熱量規劃）
- 需要 4 個輸入（身高、體重、年齡、性別）
- 有多種計算公式（Mifflin-St Jeor、Harris-Benedict 等）
- 需要明確指向下一步（TDEE、熱量赤字、進度追蹤）

**目的**：確保頁面顯示完全正確，從第 1 個字到最後 1 個字

### 🟢 第 3 層：代碼檢查清單

**目的**：確保代碼質量和可維護性

**必須檢查的 5 個代碼層面**：

#### 1. 類型安全

```typescript
// ✅ 好的做法
type CalculatorInput = {
  height: number; // cm
  weight: number; // kg
  age: number;
  gender: 'male' | 'female';
};

// ❌ 避免
const height = '180'; // 字符串而不是數字
```

**檢查項**：
- [ ] 所有輸入都有正確的類型
- [ ] 所有計算都使用正確的公式
- [ ] 所有輸出都有正確的單位

#### 2. 國際化 (i18n)

```typescript
// ✅ 好的做法 - 在 locales/zh.ts 中
export const zh = {
  bmiTitle: "BMI 計算器",
  bmiDescription: "計算您的身體質量指數",
};

// ❌ 避免 - 硬編碼文本
<h1>BMI 計算器</h1>
```

**檢查項**：
- [ ] 所有文本都在 locales 文件中
- [ ] 沒有硬編碼的中文或英文
- [ ] 語言切換時所有文本都更新
- [ ] 中英文翻譯準確一致

#### 3. 狀態管理

```typescript
// ✅ 好的做法 - 使用全局 Context
const { lang, setLang } = useLanguage();

// ❌ 避免 - 本地 state 導致不同步
const [lang, setLang] = useState(getBrowserLang());
```

**檢查項**：
- [ ] 語言狀態使用全局 Context
- [ ] 計算結果是否需要保存
- [ ] 是否需要跨頁面數據同步

#### 4. 可訪問性 (a11y)

```typescript
// ✅ 好的做法
<label htmlFor="height">身高 (cm)</label>
<input id="height" type="number" aria-label="身高（厘米）" />

// ❌ 避免
<input type="number" />
```

**檢查項**：
- [ ] 所有表單字段都有 label
- [ ] 所有按鈕都有 aria-label
- [ ] 顏色對比度足夠（WCAG AA 標準）
- [ ] 支持鍵盤導航

#### 5. 性能

```typescript
// ✅ 好的做法 - 使用 useMemo 避免重新計算
const result = useMemo(() => calculateBMR(input), [input]);

// ❌ 避免 - 每次渲染都重新計算
const result = calculateBMR(input);
```

**檢查項**：
- [ ] 計算在客戶端進行（無需 API）
- [ ] 沒有不必要的重新渲染
- [ ] 沒有內存洩漏
- [ ] 加載時間 < 1 秒

✅ 正確做法：
```
1. 檢查導航欄語言與頁面語言是否同步
2. 在不同頁面間切換語言
3. 確保全局語言 Context 正常工作
```

**3. 使用硬編碼的文本**

❌ 錯誤做法：
```typescript
<h1>BMI 計算器</h1>
```

✅ 正確做法：
```typescript
<h1>{t.bmiTitle}</h1>
```

### 🟡 中等陷阱

**4. 使用本地 state 而不是全局 Context**

❌ 錯誤做法：
```typescript
const [lang, setLang] = useState(getBrowserLang());
```

✅ 正確做法：
```typescript
const { lang, setLang } = useLanguage();
```

**5. 忽視用戶的下一步需求**

❌ 錯誤做法：
```
"計算完成了，用戶知道怎麼做"
```

✅ 正確做法：
```
1. 提供明確的下一步指引
2. 添加「進入 TDEE 計算」按鈕
3. 解釋結果的含義和用途
```

**6. 不生成文檔**

❌ 錯誤做法：
```
"代碼已經很清楚了，不需要文檔"
```

✅ 正確做法：
```
1. 生成診斷報告
2. 生成修改日誌
3. 生成設計指南
4. 生成交接文檔
```

### 🟢 輕微陷阱

**7. 忽視可訪問性**

❌ 錯誤做法：
```typescript
<input type="number" />
```

✅ 正確做法：
```typescript
<label htmlFor="height">身高 (cm)</label>
<input id="height" type="number" aria-label="身高（厘米）" />
```

**8. 不檢查移動端**

❌ 錯誤做法：
```
"桌面端看起來沒問題就行"
```

✅ 正確做法：
```
1. 檢查移動端（< 640px）
2. 檢查平板端（640px - 1024px）
3. 檢查桌面端（> 1024px）
```

## 🎓 核心原則總結

### 三個層次

1. **表面層**：代碼是否正確？
2. **功能層**：功能是否完整？
3. **用戶層**：用戶是否成功？⭐ **最重要**

### 三個原則

1. **全文掃描原則**：不能只看代碼，必須看頁面
2. **根本原因原則**：不能只修復症狀，必須修復根本原因
3. **系統性原則**：不能只修復一個頁面，必須修復所有相關頁面

### 成功標準

✅ 代碼無錯誤  
✅ 功能完整  
✅ 頁面顯示正確  
✅ 用戶體驗優秀
