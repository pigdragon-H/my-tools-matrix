## 為什麼需要共用骨架，而不是 6 份各寫各的

Victor 的原話：「QC 條件是不相同的，但 QC 流程與防治 AI 幻覺漂移的嚴謹是渴以相同的。」

意思是：**檢查項目**（多少字、幾個 H2、配色對不對、frontmatter 欄位）天生因內容類型而不同，沒辦法共用；但**怎麼把關**（什麼時候算過、誰能改什麼、出事了怎麼處理、怎麼證明真的上線了）應該是同一套紀律，不該每個單元各自發明一套寬嚴不一的標準。本文件就是抽出那套共同的「怎麼把關」。

## 一、五層 QC 結構（所有單元共用的形狀）

來源：`KNOWLEDGE_QC_MANUAL.md` §0「QC 的兩層結構」擴展對齊 `A_PLUS_PRODUCTION_MANUAL.md` 五道閘門。

| 層 | 性質 | 範例 | 通過方式 |
|---|---|---|---|
| **L1 結構閘門** | 自動量測，機器可判定 | 字數、章節數、frontmatter 完整性、檔案三件套是否齊全 | 跑指令，數字對就過，不需要人判斷 |
| **L2 原創性 / 防幻覺閘門** | 半自動 + 人工，最關鍵 | 內部查重、外部抽查、AI 幻覺與搬運雙檢 | 任一項不過 → 退回重寫，不得「先上量再補坑」 |
| **L2 內容品質閘門** | 人工審查 | 邏輯通順、案例可信、沒有空話套話 | 人工判斷，但需有檢查清單輔助，不能憑感覺 |
| **程式整合驗證** | 自動 + 半自動 | 型別檢查、registry 一致性、slug/關聯是否真實存在 | `tsc --noEmit` exit 0、validate 腳本全綠 |
| **提交推送 + 上線驗證** | 紀律閘門 | commit 三件套、push、Railway 重新部署、sitemap 數字、瀏覽器實際渲染確認 | HASH 是收據，三地（本機/GitHub/Railway）一致才算數 |

**任何一層紅燈 = 這篇/這支不算交付**，不是「先上線再回頭補」。

## 二、跨視窗紅線（防止 AI 幻覺漂移的最高紀律）

來源：`A_PLUS_PRODUCTION_MANUAL.md` §0（源自一次跨視窗越界事件的 Victor 訓示）。

1. **每個視窗（或每次任務）只負責 Victor 當下指派的範圍**，不擴大、不順手多做。
2. **別人的產出（commit / 檔案 / 工具 / 文章）沒有 Victor 明確指令，一行都不能動。**
3. **腳本抓到別人的紅燈 ≠ 修正的授權。** 只能做一件事：**回報事實給 Victor**，由 Victor 決定誰來修、要不要修。
4. 連「順手修一個錯字」「順手補一個欄位」都不行，除非那個欄位/檔案明確在這次任務的授權範圍內。

> 金句（A+ 手冊原文）：「腳本抓到的紅燈是事實，不是修代碼的授權。」

**這條對任何 AI（Claude、Manus、SuperNinja，任何視窗）都適用，不分單元。** 本次會話修 `prerender.mjs`、`BlogPost.tsx`、`validate-registry.mjs` 之所以成立，是因為每一次都先把根因攤開給 Victor 看、取得明確同意才動手，不是腳本紅燈自動授權去改。

## 三、AI 幻覺與搬運雙檢（防漂移的具體動作）

來源：`ORIGINALITY_POLICY.md` 第三節。

每篇/每支內容發布前必須雙檢：

1. **幻覺檢查**：案例數據、統計數字、引用是否標示為「示範/假設」，而不是偽裝成真實調查或真實來源卻無法驗證。
2. **搬運檢查**：
   - 內部查重（本站文章彼此之間是否高相似，包含開場句、套路句是否跨篇重複）
   - 外部抽查（抽 2–3 句最具體的句子丟搜尋引擎核對，命中逐字結果 → 重寫）
3. 任一項不過 → 退回重寫，**不得「先上量再補坑」**——這句話在原文件出現多次，是 Victor 反覆強調的紀律，適用所有單元。

查重門檻（`ORIGINALITY_POLICY.md` 五）：

| 指標 | 門檻 |
|---|---|
| 任兩篇本站內容最長共同連續片段 | < 60 字，≥60 字 → 重寫其一 |
| 樣板句跨篇逐字重複 | 0 次，逐字重複 → 改寫 |
| 外部精確比對命中逐字段落 | 0 段，命中 → 重寫該段 |

## 四、Gate 式硬閘門哲學（不是建議，是擋）

來源：`A_PLUS_PRODUCTION_MANUAL.md` 五道閘門 + `black-hole-defense.md` 四道閘門 + `MASS_PRODUCTION_SOP.md`。

- 閘門不是「軟性建議」，是 **exit 1 直接擋住**，擋在 `prebuild` / `pre-push hook` / CI 等自動觸發點，不依賴人記得手動跑。
- 「本機測試過」≠「GitHub 上有」≠「Railway 部署了」——這三件事必須分別驗證，缺一個都不算完成（這是 D-09 黑洞事件的教訓，本次會話的 `prerender.mjs`/`BlogPost.tsx` 修補也是照這個邏輯：CI 跑過真正的 build、merge 後看 Railway 真實部署結果，沒有跳過任何一段）。
- HASH／commit SHA 是收據：交付的證明是「commit/PR 連結 + CI 結果」，不是口頭說「我做完了」。

## 五、發現問題時的標準回報格式（不分單元）

來源：本次會話實際操作模式 + `A_PLUS_PRODUCTION_MANUAL.md` 終止協議精神。

1. **先講根因，不先講修法**：用實證（程式碼、log、截圖）說明「為什麼會這樣」，避免還沒查證就下結論。
2. **明確區分「已驗證的事實」vs「推測，需要進一步確認」**——本次會話多次發生先推測後修正的情況（例如誤判 ToolPage 沒有 canonical、誤判兩個匯率工具重複），每次都是攤開來承認、重新查證，這個習慣本身就是防漂移的核心動作，比「一次就講對」更重要。
3. **修補前先取得授權**，修補後附驗證證據（型別檢查結果、實際指令輸出），不要只說「應該沒問題」。
4. **無法驗證的部分要老實標註**，不要用推測填補成「已確認」的語氣（例如本機 sandbox 記憶體不足，無法跑完整 build，就老實寫「需要在 CI/Railway 真實環境驗證」，不要假裝驗證過）。
