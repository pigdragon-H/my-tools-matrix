| 制度 | 文件是否寫清楚 | 程式碼是否真的檢查 | 這次的處理 |

## 二、寫作風格規範：去機械化，使用人類流暢筆法

這條是這次新增的要求，不是修辭偏好，是實際的品質門檻。AI 寫作最容易被讀者一眼認出來的地方，不是用詞艱澀，是**句子結構過度規整、轉折生硬、大量使用「首先/其次/此外/總而言之」這類機械式連接詞**，讀起來像流程圖被翻譯成文字，不像一個人在跟你講清楚一件事。

**要避免的模板式開場**（已被驗證腳本擋下，命中即退件）：
- 「在當今快速發展的數位時代」
- 「隨著人工智慧的快速發展」
- 「本文將深入探討」

**更廣義的機械感**，程式碼沒辦法完全抓，要靠人工審查判斷，常見徵兆包括：每段開頭都用同一種句型起手、大量條列取代連貫段落、每個轉折都用「值得注意的是」「需要指出的是」這類贅語墊字、通篇沒有一句帶著具體判斷或立場的話，只有中性描述堆疊。

好的開頭應該直接指出讀者面臨的判斷困境，用具體情境切入，不是先鋪陳背景再繞到主題。判斷一篇文章寫得夠不夠像人在說話，最快的方法是大聲唸出來——如果唸起來卡、換氣點不自然，讀者讀起來也會卡。

## 三、三主軸金字塔血緣的正式規則化

這是這次改版真正的核心，之前這件事只在概念層面討論過，這次把它變成可以被程式碼檢查的具體規則。

### 3.1 兩套分級系統其實是同一件事，只是站在不同角度描述

機會情報單元治理文件（`OPPORTUNITY_INTELLIGENCE_PIPELINE.md`）定義的 `l4Status`，跟這份量產手冊定義的 L0-L4 成熟度分級，描述的是同一條金字塔，只是前者站在「一張情報卡的生命週期」角度，後者站在「一篇內容成熟到什麼程度」角度：

| 機會情報 `l4Status` | 量產手冊成熟度 | 對應內容形態 |
|---|---|---|
| `watch`（待觀察） | L0（訊號） | 停留在機會情報單元內部，不成為知識庫長文 |
| `caution`（應警惕） | 不適用 | 不進入任何晉升流程，僅供內部備忘 |
| `knowledge`（知識庫候選） | L1（概念解釋） | 回答「這是什麼、為什麼重要、有哪些限制」 |
| `blueprint-pending`（藍圖候選，條件未滿足） | L2（結構化方法） | 回答「如何比較、如何導入、如何評估」，但還沒有完整可執行架構 |
| `blueprint-ready`（藍圖候選，條件已滿足） | L3（商業模式） | 具備客群、收入模式、MVP、定價、護城河等完整要素，**不得留在知識庫，必須進入創業藍圖** |
| （尚未定義） | L4（可產品化交付物） | 創業藍圖進一步模板化、顧問化，屬於藍圖賽道內部的更高階分級，非本文件範圍 |

這張表最重要的一格是 L3 那一行：**知識庫文章一旦內容成熟度到達 L3，就不該繼續留在 knowledge 賽道**，即使結構、字數、詰問區塊全部合格，本質上也已經是偽裝成方法論文章的商業藍圖，這正是量產手冊第四章反覆強調的紅線，也是這次補進驗證腳本的 L3 關鍵字警報要攔的東西。

### 3.2 topicId 是血緣的具體實作，不是巧合

稽核既有代碼時發現一個重要事實：`shared/opportunities/ai-niche-tool-site-opportunity.md` 跟 `shared/blueprints/ai-niche-tool-site-blueprint.md` 共用同一個 `topicId`（`T-AI-BP-0001`）——這代表**同一個 topicId 出現在不同賽道的檔案裡，就是這條主題線正在往金字塔上層晉升的具體證據**，不是巧合，是既有的、只是從沒被明文規定下來的機制。

這次正式把它訂為規則：一篇知識庫文章如果透過 `relatedBlueprints` 連到某篇創業藍圖，理想狀況下兩者應該共用同一個 `topicId`，代表這是同一條主題線走過金字塔兩層；如果只是主題相關但不是同一條血緣（例如泛泛引用另一個領域的藍圖當延伸閱讀），兩者 `topicId` 本來就不必相同，這種情況不算錯誤。驗證腳本這次補上的檢查只降級為提醒，不擋 build，因為兩種情況都合理，只是語意不同，需要撰寫者自己判斷是不是要對齊。

### 3.3 具體的路由決策規則

寫作或審稿時，遇到以下狀況要照這個規則走，不要憑感覺判斷：

若一條機會情報要晉升知識庫，`l4Status` 至少要到 `knowledge`，且知識庫文章本身要有真正的深入研究與交叉查證，不能只是把情報卡內容展開改寫——這件事機會情報單元自己的治理文件已有更嚴格的查證要求，見 `OPPORTUNITY_INTELLIGENCE_PIPELINE.md` 第五節。若一篇正在寫的知識庫文章觸發了 L3 紅線警報，先停下來判斷：這個主題是不是其實該整篇轉移去創業藍圖，而不是想辦法把商業模式的內容硬降級描述成方法論文章硬留在知識庫，量產手冊第四章明講這是外部協作 AI 最常犯的錯。若一篇知識庫文章確認要晉升創業藍圖，除了內容本身要達到 L3 的完整要素（客群、收入模式、MVP、定價、護城河），`topicId` 也應該對齊，讓血緣在資料層級可被追溯，不是只在人的記憶裡。

### 3.4 金字塔各層之間，是必要條件鏈，不是雙向對稱關係

這件事值得講精確，因為它直接決定了程式碼該在哪裡設檢查、哪裡不該設。金字塔三層之間的關係，嚴格來說是**單一方向的必要條件鏈**：創業藍圖要成立，知識庫文章必須先存在；知識庫文章要成立，機會情報的驗證必須先發生。這條鏈只往上層需要下層走，不是下層必然會走到上層——多數機會情報卡本來就該停在 `watch`，多數知識庫文章也不該、也不會晉升成創業藍圖，這是金字塔「基座寬、頂點窄」的稀缺性設計本身要求的結果，不是覆蓋率不夠的缺陷。

反過來看，上層一旦真的存在，等於間接證明了下層的必要條件曾經被滿足過（因為晉升門檻強制要求先過下層），但這不是上層自己擁有某種特殊性質，只是同一條必要條件鏈，從另一個方向讀出來的結果。

這條邏輯直接對應到程式碼怎麼寫：**機會情報卡不會被要求「一定要有」對應的知識庫文章**（`relatedKnowledge` 只在情報卡真的宣稱已晉升、即 `l4Status` 到達 `knowledge` 以上時才檢查血緣是否對齊，見 3.2 節與驗證腳本 `opportunities` 區塊），但**知識庫文章一旦連到創業藍圖，血緣對齊的檢查是雙向都有的**（`knowledge` 區塊檢查 `relatedBlueprints`，`opportunities` 區塊檢查已晉升情報卡的 `relatedKnowledge`）——因為這兩處都是「宣稱已經晉升」的地方，宣稱了就該讓資料層級對得上，沒宣稱晉升的下層內容則完全不受此規則約束。

## 五、檔案位置與九個合法 domain

路徑：`shared/knowledge/<domain>/<slug>.md`

| domain | 中文標籤 | 用途 |
|---|---|---|
| `ai-business` | AI 商業 | 商業策略、組織、領導、轉型 |
| `ai-native` | AI 原生 | AI 原生世界觀、原生組織、人才重定義、AI Company |
| `ai-knowledge` | AI 知識基礎 | 知識基礎設施、向量庫、知識圖譜、知識管理、知識治理 |
| `ai-automation` | AI 自動化 | 工作流、RAG、內容工廠、自動化實戰、工具教學 |
| `ai-agent` | AI Agent | Agent 概念、導入、比較、ROI、記憶、安全 |
| `ai-side-hustle` | AI 副業 | 個人變現、副業 |
| `future-industry` | 未來產業 | 趨勢、產業展望 |
| `learning-center` | 學習中心 | 教學、入門 |
| `formula-insights` | 公式洞察 | 站方觀點、洞察 |

`<slug>`：英文小寫、連字號分隔、全站唯一，新增前先 `ls shared/knowledge/<domain>/` 確認不撞名。外部 AI 不得自行創造新的 domain。

## 六、Frontmatter 必填欄位

```yaml
---
id: <同 slug>
title: { zh: "中文標題（含副標）", en: "English Title" }
description: { zh: "中文摘要 60-120 字", en: "English summary" }
keywords: ["主關鍵字", "長尾1", "長尾2", "…6-8 個"]
publishedAt: YYYY-MM-DD
domain: <九個合法值之一>
relatedTools: ["/tools/ai/...", "..."]
contentType: knowledge
topicId: T-AI-KB-XXXX          # 全站唯一，掛載到 shared/aiTopics.ts；若此文章對應某篇創業藍圖的同一條主題線，兩者 topicId 應對齊
operatingStatus: active
ctaType: knowledge_next_question
signal: ["需求訊號1", "訊號2"]
output: ["pillar definition node", "..."]
relatedBlueprints: []
relatedOpportunities: []
relatedKnowledge: ["3-4 個同站相關 slug，須真實存在"]
affiliateTags: ["..."]
newsletterCta: true
adsEnabled: true               # 正式文 true；草稿 false
---
```

`relatedKnowledge`/`relatedBlueprints`/`relatedOpportunities` 裡的每個 slug 都必須真實存在，否則 `validate-ai-three-axes` 報錯。`topicId` 必須唯一，新增前查詢目前最大編號（截至這次改版是 `T-AI-KB-0201`，下一個可用是 `0202`）。


## 八、QC 結構閘門（程式碼已強制檢查的部分）

```bash
node scripts/validate-ai-three-axes.mjs
```

這支腳本目前對 knowledge 賽道實際檢查：字數 ≥3000 字元、H2 數量 8-10、詰問區塊恰好一個且格式正確（3題、每題粗體、每題含「引導思路」、位置在結語前）、至少一個表格、至少一個框線圖、L3 紅線關鍵字（警告）、模板式開場（錯誤）、跨軸關聯 slug 存在、`topicId` 唯一、與創業藍圖的血緣對齊（警告）、`topicId` 是否登記在 `docs/task-cards/registry.json`（警告，debt-tracking）。同一支腳本也對 opportunities 賽道新增了對稱的檢查：`l4Status` 已晉升到 `knowledge` 以上時，`relatedKnowledge` 是否有與其血緣對齊的 `topicId`（警告）。

```bash
npm run check:originality
```

這支指令會跑 60 字 n-gram 比對，抓出文章之間的高相似/逐字重複片段。**這個工具查的是站內文章彼此之間有沒有逐字複製同一套模板句**，不是要求每篇文章的概念或工具組合完全獨創——依 Victor 的定調，AI 工具本身是可以被不同題目重複運用、重新排列組合的，天下概念一大抄，這件事本身不是問題，真正不可以的是**題目相同、內容卻高度雷同**。這件事的判斷基準是「slug/`topicId` 是否唯一」，這條規則已經由第六節的 frontmatter 檢查強制執行；n-gram 比對只是額外的一道保險，用來抓「換了題目、但整段照抄舊文章模板句」這種取巧行為，**不需要也不必要接進自動化 CI 擋 build**，維持人工不定期抽查即可，見第十節。

## 九、QC 品質閘門（人工審查）

- [ ] 差異化：與同主題既有文切入角度明顯不同
- [ ] 事實正確：數字/日期/專有名詞可被合理支撐，無明顯幻覺
- [ ] 可操作：架構圖、可用 Prompt、導入 SOP、ROI 算法俱全且能落地
- [ ] 內鏈正確：`/knowledge/...`、`/tools/...` 連結路徑指向存在頁面
- [ ] 可讀性：無贅字、無 AI 腔同質化（見第二節去機械化規範）
- [ ] 無絕對化空話：少用「最好」「一定」等未經支撐的絕對宣稱
- [ ] L3 紅線：若驗證腳本發出警報，人工確認這是不是該轉移去創業藍圖
- [ ] 主題唯一：確認題目本身（不是工具或概念）沒有跟既有文章重複，工具、概念重疊不算問題
