# 機會情報單元治理準則：三層金字塔模型

版本：v1.0
核准日期：2026-07-01
適用範圍：機會情報單元 / AI知識庫 / AI創業藍圖，三軸協作的所有AI執行者（Claude、SuperNinja、Manus）
文件定位：本文件是三方AI判斷「一條情報該停在金字塔哪一層」的唯一依據，任何AI執行者在處理情報卡時，不得依個人理解另訂標準。

---

## 一、核心原則

情報不是終點，是三主軸共用的血液。機會情報單元、AI知識庫、AI創業藍圖不是三個平行的內容分類，是同一份原料經過逐層篩選後的三種濃縮形態：

```
機會情報單元（基座，全部原料）
    ↓ 晉升門檻一
AI知識庫文章（中層，查證通過的模式）
    ↓ 晉升門檻二
AI創業藍圖（頂點，稀少且可執行）
    ↓ 使用數據回饋
（回到機會情報單元，形成閉環）
```

**基座越寬，價值密度越低；頂點越窄，價值密度越高。** 藍圖的稀缺性不是刻意營造的行銷話術，是三層篩選的自然結果——不是每條情報都配得上藍圖，這件事本身就是藍圖付費正當性的來源。

## 二、三層定義與晉升門檻

### 第零層：機會情報單元（基座）

**收錄條件：** 任何原料，不設門檻，先收再說。原料可能是X貼文、GitHub專案、產業報導、任何形式的一手或二手信號。

**必要處理：** 每條原料進入基座時，必須跑完四層分析（見第三節），並填寫完整的情報卡欄位（見第四節）。未跑完四層分析的原料，不算正式收錄，只算「待處理佇列」。

### 第一層：AI知識庫文章（中層）

**晉升門檻（須同時滿足）：**

1. **跨來源交叉驗證**：至少兩個獨立來源（不同帳號、不同平台、不同時間點）反覆指向同一個模式、缺口或現象。單一來源的孤證，即使內容紮實，也不足以晉升，只能停留在基座作為「待觀察信號」。
2. **查證通過**：情報卡中涉及的具體數字、政策宣稱、案例真實性，已依第五節的強制查證規則處理完畢，且未被推翻。政策幻覺、案例幻覺類原料一律不得晉升。
3. **具備L2/L3層級的結構判讀與缺口判讀**：情報卡不能停留在L1表層摘要，必須能講清楚「這反映了什麼現象」「現有方案沒覆蓋到什麼」。

**產出形式**：知識庫文章負責回答「為什麼」——解釋現象、拆解方法論、提供讀者可自行判斷的框架。文章不直接提供逐步可執行的操作方案，那是藍圖層的工作。

### 第二層：AI創業藍圖（頂點）

**晉升門檻（須同時滿足，且以第一層晉升為前提）：**

1. **對應的知識庫文章已存在**：藍圖不能憑空產生，必須先有一篇已發布的知識庫文章，證明FU已經完整論證過這個主題的動機與價值。
2. **具備完整可執行的架構或完成模型**：不是「這裡有個缺口」，是「這裡是怎麼填的」——包含具體步驟、所需資源、預期產出、驗收標準。停留在「缺口存在但無人解決」階段的主題（例如目前的短劇角色一致性問題），即使知識庫文章已經寫得很完整，也不得晉升藍圖，應標記為「藍圖候選，晉升條件未滿足」，持續追蹤直到出現可執行方案。
3. **具備稀缺性檢驗**：能通過「用戶願不願意為這份執行方案付費」的檢驗。如果答案顯而易見（免費資訊唾手可得），則不構成藍圖，應留在知識庫層。

**產出形式**：完整可執行的架構文件，可能採付費模式。血緣可回溯至原始機會情報與對應知識庫文章。

### 反饋閉環：藍圖 → 機會情報

藍圖一旦有使用者採用，其使用數據（採用率、常見卡點、參數調整偏好、衍生需求）本身即構成新的機會情報原料，且是全站唯一、任何第三方無法複製的一手數據。此類數據應以「內部一手數據」標籤重新進入基座，觸發下一輪的分析與判讀。

## 三、四層分析框架（每條原料必跑）

| 層級 | 問題 | 目的 |
|---|---|---|
| L1 表層 | 這是什麼？ | 純摘要，無價值判斷 |
| L2 結構 | 這類信號背後反映什麼市場現象？ | 找模式，不是找單點 |
| L3 缺口 | 現有方案沒覆蓋到什麼？誰會需要但找不到？ | 這才是「機會」 |
| L4 動作 | 這條原料目前該落在金字塔哪一層？ | 決定後續路由 |

L4欄位不再是自由文字，必須從以下選項中擇一：

- `基座-待觀察`：單一來源，尚無交叉驗證，暫留基座
- `基座-應警惕`：判定為詐騙話術、合規風險內容，不進入任何晉升流程，僅作內部備忘
- `知識庫候選`：已滿足第一層晉升門檻，可產出文章
- `藍圖候選-條件未滿足`：知識庫文章已存在或可產出，但缺乏完整可執行架構，需持續追蹤
- `藍圖候選-條件已滿足`：可進入藍圖產出流程


## 五、強制查證規則

以下情況觸發強制查證，查證未通過前，信心分數不得高於2分，且不得晉升任一層級：

1. **具體時間點的政策/法規宣稱**（例如「X月起監管收緊」）——曾實際發生查證未通過案例（見案例庫#11），此類宣稱極易將「感覺」包裝成「事實」。
2. **無法追溯來源的具體收入/成效數字**（例如「月入X萬」「賺了X美元」）——若無可查證的具名來源、後台截圖、第三方報導佐證，一律視為案例幻覺，不得引用具體數字，僅可萃取方法論骨架。
3. **「我有N個XX但一個都不露」類結構**——鉤子文案的典型特徵，預設信心分數1分，除非後續補上可驗證內容才升級。

## 七、來源帳號信譽層（獨立於單條情報評分）

單條情報的信心分數與來源帳號的長期信譽，須分開追蹤。同一帳號重複出現三次以上時，正式建立信譽評級：

- **彙整型帳號**：內容廣但驗證深度不足，需逐條個別查證，不可預設信任
- **一手實測型帳號**：具名、附證據、可信度較高，可適度提高預設信心分數
- **應規避型帳號**：曾產出「應警惕」類內容（詐騙結構、合規風險），後續內容需以最高規格查證

## 九、AdSense與商業化合規閘門

本節處理的是「內容一開始該不該被收錄」，屬於比第五節更前置的守門機制，兩者互補、不重複。第五節處理的是「內容已收錄後，可信度該打幾分」。

### 9.1 情報蒐集階段的排除規則（適用範圍：L0蒐集當下，不進入基座）

**規則一（加密貨幣/投機性金融商品排除）**

機會情報單元禁止採集涉及加密貨幣投資、交易訊號、或投機性金融商品銷售的信號內容，並應主動減少對相關特定標的（幣種、交易平台、跟單/自動交易工具）的報導。此類主題不屬於FU機會情報單元的蒐集範圍，於原料進入待處理佇列前即應排除，不建立情報卡。

例外：若信號本身屬於技術工具類（例如區塊鏈開發框架、非投資性質的加密技術應用），仍可收錄，但情報卡須明確標註「非金融投資屬性」以資區別。

**規則二（不可查證財務收益排除）**

機會情報單元禁止採集核心建立在無可查證財務收益數字、或不切實際宣稱之上的報導。此類原料若已進入待處理佇列，經第五節強制查證規則判定查無可信來源佐證者，一律標記為`基座-應警惕`，不得進入知識庫或藍圖晉升流程，亦不得以任何改寫形式保留具體數字。

### 9.2 判斷依據：Google對「金融產品與服務」的精確定義

Google對金融產品與服務的定義，是指涉及金錢與加密貨幣的管理或投資的內容，包括個人化建議，具體包含個人貸款、加密貨幣交易平台、二元期權、特定投資產品，以及對報酬做出宣稱卻沒有適當揭露的內容。複雜投機性金融產品（差價合約、外匯保證金交易等）及提供其交易訊號的內容目的地，皆受此政策限制。

FU機會情報單元的核心主軸是AI技術創新、創業方法論、生產力應用，本質上與此定義無關。只要源頭排除加密貨幣/投機交易類信號、並禁止收錄不可查證的財務數字，機會情報單元產出的知識庫文章與藍圖，就不會落入Google的金融限制類別，也不會觸及「不實陳述」政策風險（該政策明確禁止對財務收益做出誤導性或不切實際的宣稱）。這兩條規則等同於直接把整個單元鎖定在安全區內，不需要每篇文章上線前再單獨審查主題合規性。

### 9.3 與現有情報卡的回溯適用

依本節規則回溯檢視既有情報卡：#18（Polymarket自動交易機器人）為目前唯一命中規則一之案例，本即已標記為`基座-應警惕`，不受影響。其餘情報卡主題（AI技術工具、創業方法論、內容變現策略、電商定價、知識付費）均不落入金融產品與服務定義範圍，僅受規則二（財務數字查證）約束，此規則已與第五節強制查證規則一致，無需額外處理。

## 十、資訊隔離原則

### 10.1 核心問題：UI層隱藏欄位，不等於資料未外洩

第一筆正式情報卡（ic-2026-0012）產出時發現一項架構缺陷：`sourceUrl`等內部查證用欄位若與公開展示欄位存放於同一資料物件，即使前端UI設計為不渲染該欄位，該欄位仍會存在於API回應的JSON中，任何使用者透過瀏覽器開發者工具即可直接讀取，等同於情報來源完全曝光，第五、六節建立的脫源工程與帳號信譽治理將全數失效。此問題不能靠前端顯示邏輯或人工自律解決，須由資料架構層面物理隔離。

### 10.2 兩層資料模型

情報卡資料須明確區分為兩個獨立型別：

- **內部層（Internal）**：包含來源URL、原始文字片段、帳號信譽備註、完整血緣關聯等一切可用於反推信號來源的欄位，僅存在於伺服器端與內部治理視圖，永不透過公開API序列化。
- **公開層（Public）**：僅包含經脫源工程處理後、不可反推來源的欄位（摘要、模式判讀、缺口判讀、信心分數、L4狀態、主賽道、次要標籤、對外衍生物連結）。

技術定義詳見 `INTELLIGENCE_CARD_COMPONENT_SPEC.md` 第二節。

### 10.3 白名單序列化鐵律

**所有面向使用者的公開API端點，一律採用白名單方式挑選欄位組成回應，禁止傳輸完整內部物件後交由前端自行篩選顯示。** 後者是常見的資料外洩模式——前端不顯示，不代表資料未離開伺服器。此鐵律適用於機會情報單元的所有現在與未來端點，不因元件重構、API改版而例外。

### 10.4 白名單治理：風險不對稱原則

白名單本身並非一成不變，隨產品發展可能需要增減欄位，但**增加與移除的風險並不對稱，治理規格須反映此不對稱性**：

| 操作 | 風險等級 | 治理要求 |
|---|---|---|
| 從白名單**移除**欄位 | 低風險（縮小公開面） | 可隨時執行，視為修訂版本，僅需於變更紀錄註記 |
| 對白名單**新增**欄位 | 高風險（擴大公開面，可能重新引入洩漏） | 須先通過以下審查清單，經確認後方可執行，並於變更紀錄詳細記載理由 |

**新增欄位審查清單（須逐項確認）：**

1. 此欄位內容是否可能包含或間接還原來源URL、帳號名稱、或逐字引用片段？
2. 此欄位是否可能被交叉比對其他公開資訊（如該情報卡的發布時間、主題），反推出原始信號來源？
3. 此欄位對讀者/使用者的實際必要性，是否高於其潛在洩漏風險？

三項皆通過方可新增；任一項有疑慮，該欄位應留在內部層，改以摘要化、去識別化的替代欄位呈現。

### 10.5 技術實作對應

型別定義與執行期白名單須共用同一份陣列常數作為單一事實來源，禁止型別定義與實際序列化邏輯各自維護、彼此可能漂移不一致的寫法。實作範例詳見 `INTELLIGENCE_CARD_COMPONENT_SPEC.md`。

|---|---|---|---|

### 10.7 公開層文字黑名單詞彙與替換規則

第10.2至10.6節處理的是「哪些欄位可以公開」，本節處理更細一層的問題：**即使是允許公開的文字欄位（summary、patternInsight、gapInsight），內容本身仍可能夾帶暴露內部身分或協作架構的詞彙**。此類欄位屬於編輯改寫產出，不是單純的欄位挑選（pick），因此無法靠白名單機制自動處理，須建立獨立的詞彙替換規則。

**強制替換對照表：**

| 內部詞彙 | 公開層替換為 | 說明 |
|---|---|---|
| FU／Formula Universe／本站／我們公司 等公司自稱 | 企業 | 避免曝露內容洞察與特定公司內部狀態的直接關聯 |
| Manus | AI agent | 避免曝露內部協作工具鏈組成 |
| SuperNinja | AI agent | 同上 |
| Claude（作為內部執行角色描述時，例如「我方用Claude執行XX」） | AI agent／AI 助手 | 若情境是討論Claude作為公開可查證的技術本身（如工具評測、產品比較），不在此替換範圍內，僅替換「內部使用場景」的描述 |

**執行規則：**

1. 此表為初版，非窮舉清單，日後可持續擴充（例如新增內部專案代號、其他協作工具名稱），擴充方式比照第10.4節白名單治理精神：新增詞彙隨時可做（降低曝露風險，屬安全方向），但不得任意「移除」表列詞彙的替換要求。
2. 公開層文字欄位（summary、patternInsight、gapInsight）產出時，須先過本表逐項掃描替換，才可視為完稿，不可等發布後才發現遺漏。
3. 建議比照現有 `scripts/check-duplicate.mjs` 的治理模式，日後建立對應的自動化掃描腳本（例如 `scripts/check-public-content-blocklist.mjs`），在內容產出流程中做程式化檢查，不完全依賴人工記憶與臨場判斷。



## 十一、與既有機會情報系統的整合對接（2026-07-01）

### 11.1 發現：機會情報單元並非全新建置

實作階段查證發現，`shared/opportunities/`底下已有既有的正式schema（`OpportunityMeta`，定義於`shared/laneSchemas.ts`）與3篇已發布文章，且有專屬QC驗證腳本（`scripts/validate-ai-three-axes.mjs`）長期在跑。既有系統原本以`marketDemand`（AI推論的市場需求強度：high/medium/low）作為機會情報單元唯一的分類軸，且此軸與知識庫（domain分類）、創業藍圖（industry分類）兩個賽道的分類邏輯不一致——機會情報是三軸裡唯一不用「領域」分類的賽道。

### 11.2 概念層級澄清：情報卡（IntelligenceCard） vs 機會情報文章（OpportunityMeta）

本治理文件第一節起設計的「情報卡」，對應的是金字塔**最底層、最原始的單條信號**——可能有數十上百條，多數停留在`watch`狀態，只有少數晉升。既有的`OpportunityMeta`則是**已經產出的正式機會情報文章**本身的schema，通常已綜合多條信號、經過編輯撰寫，性質上更接近本文件金字塔模型裡「已晉升、值得完整論述」的產物。兩者是**不同海拔的兩層概念**，不是同一份資料的重複定義：

```
機會情報單元（大量原始情報卡，多數internal，不公開）
    ↓ 少數晉升
機會情報文章（OpportunityMeta，公開發布，即 shared/opportunities/*.md）
```

### 11.3 已完成的欄位整合

`OpportunityMeta`新增/變更如下，2026-07-01實作：

| 欄位 | 異動 | 說明 |
|---|---|---|
| `domain` | 新增 | 主賽道分類，值集合定義於`client/src/lib/laneCategories.ts`的`CATEGORY_LABELS.opportunities`，**刻意不用enum鎖死**，可持續擴充——比照本文件第六節「主賽道分類可持續擴充」原則，且驗證腳本僅檢查非空字串，不做列舉限制 |
| `l4Status` | 新增 | 對應本文件第三節L4狀態五選一，用`Set`在驗證腳本鎖死合法值 |
| `fuRating` | 新增，取代`marketDemand` | **FU團隊人工評分（1-5星）**，取代原本AI主觀推論的需求強度分級。此欄位代表人的判斷，不是AI的猜測，兩者性質不同不應混用 |
| `blueprintCandidate` | 語意變更 | 保留為向後相容欄位，語意上應等於`deriveBlueprintCandidate(l4Status)`的結果，驗證腳本會在兩者不一致時發出警告（非強制error，允許漸進修正既有資料） |

首批domain值集合實作時發現既有3篇文章有1篇（AI利基工具站機會）不落在原先設想的5條主賽道任何一條裡，因此新增第6個值`productized-web-tools`——**這正好是「不可鎖死5條賽道」這條規則在真實資料上的驗證**，證明擴充機制是必要的，不是理論假設。

### 11.4 尚未處理的既有技術債（本次不在範圍內）

執行`npm run validate:ai-three-axes`時發現`shared/knowledge/`底下大量既有文章缺少`topicId`登記、`signal`/`output`欄位、跨軸關聯——這是既存於本次整合之前的技術債，與本次機會情報schema變更無關，本次不予處理，留待後續獨立排查。
