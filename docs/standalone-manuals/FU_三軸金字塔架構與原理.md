# Formula Universe 三軸金字塔架構與原理

版本 v1.0 · 2026-07-03 · 整理者：Claude（Universe Auditor / QC）
性質：**共用基礎文件**，說明機會情報、AI知識庫、AI創業藍圖三個內容軸如何組成一座金字塔、彼此如何連動。三份各軸獨立操作手冊（`機會情報格式規範與QC操作手冊`、`AI知識庫文章撰寫與QC操作手冊`、`創業藍圖格式規範與QC操作手冊`）分別可獨立交付給不同任務AI執行，但建議每個任務AI在開工前先讀過這份文件一次，理解自己正在做的事在整體架構裡的位置。

---

## 一、核心原則

情報不是終點，是三主軸共用的血液。機會情報、AI知識庫、AI創業藍圖不是三個平行的內容分類，是同一份原料經過逐層篩選、逐層加工後的三種濃縮形態：

```
機會情報（基座，全部原料，決策備忘性質）
    ↓ 晉升門檻一：跨來源交叉驗證 + 查證通過
AI知識庫（中層，深度解析的長文）
    ↓ 晉升門檻二：知識庫文章已存在 + 具備完整可執行架構
AI創業藍圖（頂點，稀少・可執行・可能付費）
    ↓ 使用數據回饋
（回到機會情報，形成閉環）
```

基座越寬，價值密度越低；頂點越窄，價值密度越高。藍圖的稀缺性不是行銷話術，是三層篩選的自然結果，也是它能收費的正當性來源。

## 二、金字塔各層之間，是必要條件鏈，不是雙向對稱關係

這件事值得講精確，因為它直接決定了三軸的數量關係、也決定了程式碼該在哪裡設檢查。

金字塔三層之間的關係，嚴格來說是**單一方向的必要條件鏈**：創業藍圖要成立，知識庫文章必須先存在；知識庫文章要成立，機會情報的驗證必須先發生。這條鏈只往上層需要下層走，不是下層必然會走到上層。

**有意義運作時，三軸的數量關係應該是：機會情報數量 > AI知識庫數量（扣除專有名詞解釋類文章）>> AI創業藍圖數量。** 這不是覆蓋率不夠的缺陷，是金字塔「基座寬、頂點窄」的稀缺性設計本身要求的結果——多數機會情報卡本來就該停在「待觀察」，多數知識庫文章也不該、也不會晉升成創業藍圖。**三軸不是1對1衍生關係**：如果每條情報都強制要有對應的知識庫文章、每篇知識庫文章都強制要有對應的藍圖，等於變相把三軸拉平成同一件事的三種格式，創業藍圖會失去稀缺性帶來的價值，整座金字塔就垮了。

反過來看，上層一旦真的存在，等於間接證明了下層的必要條件曾經被滿足過（因為晉升門檻強制要求先過下層），但這不是上層自己擁有某種特殊性質，只是同一條必要條件鏈，從另一個方向讀出來的結果。

**這條邏輯直接對應到規則設計：**
- 下層永遠不會被要求「一定要有」對應的上層內容（機會情報不強制要有知識庫連結、知識庫文章不強制要有藍圖連結）
- 但只要下層宣稱已經晉升（機會情報的 `l4Status` 標記為 `knowledge` 以上、或知識庫文章實際連結了某篇藍圖），血緣對齊的檢查就該生效，要求兩者誠實對應，不能宣稱晉升卻血緣對不上

## 三、兩套分級系統是同一件事，只是站在不同角度描述

`OpportunityMeta.l4Status`（機會情報卡的生命週期分級）跟量產手冊的 L0-L4 成熟度分級（內容成熟度分級），描述的是同一條金字塔，只是前者站在「一張情報卡的生命週期」角度，後者站在「一篇內容成熟到什麼程度」角度：

| 機會情報 `l4Status` | 量產手冊成熟度 | 對應內容形態 |
|---|---|---|
| `watch`（待觀察） | L0（訊號） | 停留在機會情報單元內部，不成為知識庫長文 |
| `caution`（應警惕） | 不適用 | 不進入任何晉升流程，僅供內部備忘 |
| `knowledge`（知識庫候選） | L1（概念解釋） | 回答「這是什麼、為什麼重要、有哪些限制」 |
| `blueprint-pending`（藍圖候選，條件未滿足） | L2（結構化方法） | 回答「如何比較、如何導入、如何評估」，但還沒有完整可執行架構 |
| `blueprint-ready`（藍圖候選，條件已滿足） | L3（商業模式） | 具備客群、收入模式、MVP、定價、護城河等完整要素，**不得留在知識庫，必須進入創業藍圖** |
| （尚未定義） | L4（可產品化交付物） | 創業藍圖進一步模板化、顧問化，屬於藍圖賽道內部更高階分級 |

L3 那一行最重要：**知識庫文章一旦內容成熟度到達 L3，就不該繼續留在 knowledge 賽道**，即使結構、字數、格式全部合格，本質上也已經是偽裝成方法論文章的商業藍圖。

## 四、topicId 是血緣的具體實作，不是巧合

稽核既有代碼時發現一個重要事實：`shared/opportunities/ai-niche-tool-site-opportunity.md` 跟 `shared/blueprints/ai-niche-tool-site-blueprint.md` 共用同一個 `topicId`（`T-AI-BP-0001`）——同一個 topicId 出現在不同賽道的檔案裡，就是這條主題線正在往金字塔上層晉升的具體證據。

一篇下層內容如果透過 `relatedKnowledge`／`relatedBlueprints` 連到上層，理想狀況下兩者應該共用同一個 `topicId`，代表這是同一條主題線走過金字塔兩層；如果只是主題相關但不是同一條血緣，兩者 `topicId` 不必相同，這種情況不算錯誤，只是「相關內容」不是「血緣晉升」。

## 五、公開文章的傳動軸：AI視角區塊與「往知識庫閱讀」雙狀態接點

情報卡層級的血緣（`topicId` 對齊）是資料層的機制，訪客看不到。但機會情報**公開發布的文章**，必須有一個訪客真正看得到、點得下去的傳動接點，讓讀者能親手感受到金字塔在運作，這個接點是「🔭 AI視角」區塊裡的「往知識庫閱讀」雙狀態接點：

- **有對應知識庫文章時**：`往知識庫閱讀 → [標題](/knowledge/slug)`，一個真連結
- **還沒有對應知識庫文章時**：`往知識庫閱讀 → 無知識庫文章`，誠實聲明，不硬塞一個牽強的連結充數

兩種狀態都合法，但兩者都不寫才算違規——這是「傳動軸一定要接上，但接去哪裡不強迫」的具體實作。

### ⚠️ 常見錯誤（真實事故，2026-07-03）：三軸網址格式不對稱，寫連結前務必先查對

三軸的網址格式**不是統一規則**，這是最容易犯錯、也真的出過事故的地方：

| 賽道 | 正確網址格式 | 段數 |
|---|---|---|
| 機會情報 | `/opportunities/{slug}` | 1段 |
| 創業藍圖 | `/blueprints/{slug}` | 1段 |
| **知識庫** | `/knowledge/{domain}/{slug}` | **2段，多一層domain** |

**只有知識庫是兩段式**，機會情報跟創業藍圖都是單段。真實發生過的事故：AI視角區塊寫連結時，直接套用機會情報自己的單段慣例，寫成`/knowledge/{slug}`（漏掉domain段），結果這個網址完全沒對上任何路由規則，訪客點下去看到的是一片空白（且事故當時全站還沒有404兜底頁面，訪客連返回的路都沒有，此問題已於同日修復，見下方）。

**寫任何指向知識庫文章的連結之前，必須先去查該篇知識庫文章frontmatter裡的`domain`欄位實際值是什麼**，不能用猜的、不能假設跟機會情報自己的domain一樣（機會情報跟知識庫的domain值集合本身就是分開維護的兩套，不保證同名同值）。驗證腳本現在會擋下格式錯誤的連結（`scripts/validate-ai-three-axes.mjs`），但事先查清楚比事後被擋下重寫更有效率。

同一起事故也暴露了一個更大的問題並已修復：當時全站沒有任何404兜底路由，任何格式錯誤的網址都會讓訪客卡在空白頁面、無路可退。現在已加上全站兜底404（`client/src/App.tsx`的`<Route path="*">`），但這不代表可以因此就不謹慎寫連結——兜底頁面是安全網，不是允許犯錯的理由。

## 六、全站共用的寫作與合規規則（三軸皆適用）

- **去機械化，使用人類流暢筆法**：禁止模板式開場（如「在當今快速發展的數位時代」），廣義的機械感（過度規整的句子結構、大量條列取代連貫段落）靠人工審查判斷，程式碼只能抓最明顯的模板句
- **不可虛構具體數字**：任何具體財務/統計數字，若非企業自己第一手驗證過的真實資料，一律不得寫進公開文章，這是查證優先原則的延伸
- **黑名單詞彙**：公開文章不得出現內部協作工具/團隊代號（如 Manus、SuperNinja），一律以「AI agent」等通用說法替代
- **加密貨幣/投機性金融商品排除**：不採集也不發布涉及加密貨幣投資、交易訊號、投機性金融商品的內容
- **主題唯一**：不同文章的題目本身不可重複，但工具、概念、技術組合可以在不同題目下重複運用——依 Formula Universe 的定調，AI工具本身就是會被排列組合、重新應用在不同題目上的技術，不是公式，重複運用不是問題，題目重複才是問題

## 七、三方AI角色分工

| 執行者 | 負責範圍 |
|---|---|
| Victor（人工） | X端等一手情報蒐集、最終晉升決策、創業藍圖上架前的人工審查（`victorReviewed` 關卡） |
| Claude | 四層分析、查證、情報卡與文章產出、跨軸血緣比對、QC稽核 |
| Manus | 非X端自動化來源、技術方案實測、排程執行 |
| SuperNinja | 內容寫作與UI執行 |

外部協作AI（含 Claude）不擁有上線權，也不擁有 L3 判定或創業藍圖最終核可的權限，可以建議、可以標記，不能自行拍板。

## 九、商業層規範：AdSense／Affiliate／Premium（三軸共用架構）

三軸共用同一套商業層元件（透過 `ArticleShell`），不是各自獨立設計，撰稿時只需理解機制、填對欄位，不需要手動處理版位插入。

**AdSense（`AdSlot`，自動插入，不可手動下指令）**：固定位廣告4個，由系統自動在開場引言後、正文約1/3處、約2/3處、正文結尾插入；動態曝光廣告則是每出現一個表格、每出現一個以框線字元（`┌┐└┘├┤┬┴┼─│▶►→↓↑`）繪製的架構圖，其下方各自動增生一個廣告位。**這正是三軸QC規則都要求至少一個表格、至少一個框線圖的商業原因之一**——這兩個元素直接決定文章能吃到幾個額外曝光位，不只是內容豐富度考量。唯一控制欄位是 `adsEnabled`（草稿 `false`，正式發布 `true`）。廣告絕不可手動寫進 markdown 正文，一律由元件自動注入。

**Affiliate（`affiliateTags`，現行可用）**：frontmatter 填 `affiliateTags: [...]`，透過 `filterAffiliatesByTags(賽道, tags)` 自動比對顯示相關聯盟商品/工具推薦。標籤應對應內文實際提及、且有商業關聯的具體工具/服務名稱，不要塞不相關標籤湊數。

**Premium（`premiumGate`，目前未啟用，規劃時務必注意）**：`PremiumGate` 元件與三軸的 `premiumGate`／`premiumGatePosition` 欄位都已存在，但控制其生效的功能開關 `ENABLE_PREMIUM` 目前是關閉狀態。**關閉狀態下，設 `premiumGate: true` 不會產生任何付費牆效果，內容照樣完全公開顯示**，付款串接（Stripe）也還未接上。若規劃的內容倚賴 premium 變現，撰寫前務必先跟 Victor 確認商業開通時程，不能假設設了欄位就會生效。
